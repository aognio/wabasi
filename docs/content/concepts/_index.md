# Concepts

## The Wakaba World

One Wakaba instance is one isolated, locally controllable simulated messaging world.

```
Human UserAccounts
        │
        └── operate VirtualIdentities

VirtualIdentities
        │
        ├──── communicate with other VirtualIdentities
        │
        └──── communicate with BusinessPhoneNumbers

Businesses
        │
        └── WABAs
              │
              └── BusinessPhoneNumbers

Applications / CRMs
        │
        └── connect to BusinessPhoneNumbers
             through the Meta-compatible
             Business Platform boundary
```

All messaging passes through Wakaba's common messaging infrastructure.

## Participants

### VirtualIdentity

A simulated consumer participant. Created by humans through the Virtual Client or API.

- Has a phone number (E.164 format)
- Has a display name
- Can communicate with other VirtualIdentities
- Can communicate with BusinessPhoneNumbers
- Does NOT require any business entity to function

### BusinessPhoneNumber

A business participant. Represents a phone number owned by a WABA.

- Has a phone number (E.164 format)
- Belongs to a WABA, which belongs to a Business
- Is an addressable participant at the messaging level
- The Business Platform adapter exposes its integration to external software

### Key Distinction

UserAccount ≠ VirtualIdentity. One human may operate multiple VirtualIdentities. Being able to discover another identity does not grant permission to operate it.

## Phone Number Registry

All phone numbers (consumer + business) share one global uniqueness domain.

- A number belongs to exactly one addressable participant
- E.164 normalized storage
- Centralized allocation enforces uniqueness

## Conversations

A Conversation is a direct relationship between two participants:

```
Conversation
    Participant A
    Participant B
```

Both `Alice ↔ Bob` and `Alice ↔ ACME Support` use the same fundamental conversation/message machinery. Business-specific metadata is layered around the latter when necessary.

## Messages

Messages have a sender, recipient, type, and status progression:

```
pending → accepted → sent → delivered → read
                                    → failed
```

Direction is perspective-derived. For `Alice → Bob`, the message is outgoing for Alice and incoming for Bob. Core truth is: sender, recipient.

### Message Types

- Text, Image, Video, Audio, Document
- Location, Contacts
- Template, Interactive, Reaction

## Media

Media is part of the Wakaba world, not specifically the Business API.

Consumer-consumer media uses the same underlying subsystem as consumer-business media. Internally, Wakaba uses content-addressable storage (CAS) for deduplication, but this is transparent to integrations.

## Business Platform as Adapter

The Business Platform is an adapter over the messaging core:

```
CRM → Meta-compatible API → Business Platform Adapter → Messaging Core → Alice
```

and:

```
Alice → Messaging Core → Business participant → Business Platform Adapter → Webhook → CRM
```

The Business API is not Wakaba's messaging engine. It is an integration boundary.

## Webhooks

Webhooks are generated by the Business Platform adapter when business-relevant events occur. They carry:

- Message content or status updates
- HMAC-SHA256 signatures for verification
- Exponential backoff retry logic

Webhooks are only relevant for business traffic. Consumer-to-consumer messaging does not generate webhooks.

## Observability

Wakaba records structured operational evidence:

- **Events** — discrete facts (what happened)
- **Traces** — causal relationships (how it happened)
- **Metrics** — aggregated measurements (how often, how fast)
- **Diagnostic Findings** — analytical conclusions supported by evidence

This enables reconstruction of any interaction from creation to final state.
